Abstract
The fragmented and paper-driven nature of healthcare record management in India presents significant operational and clinical challenges for local clinics, multispecialty hospitals, and diagnostic laboratories. This paper presents HealthCore SaaS — a multi-tenant, cloud-native healthcare management platform designed to digitize and unify clinical workflows across heterogeneous medical facilities. The system employs a decoupled three-tier architecture comprising a React 19 single-page application frontend, a FastAPI asynchronous REST backend, and a Supabase-hosted PostgreSQL database enforced with Row-Level Security (RLS). Key contributions include: (1) a scoped Role-Based Access Control (RBAC) model ensuring strict data isolation between tenants; (2) a full clinic management suite encompassing patient registration, appointment scheduling with real-time slot computation, walk-in queue management, electronic prescriptions with PDF generation, and invoicing; (3) a laboratory management subsystem covering test catalogues, order lifecycle, sample tracking, result validation, and diagnostic report delivery; (4) a patient-facing self-service portal for provider discovery and direct appointment booking; and (5) an emergency ambulance dispatch module with simulated GPS tracking. The platform achieves horizontal scalability through asynchronous I/O and stateless API design, while maintaining HIPAA-aligned data security through JWT authentication and PostgreSQL RLS policies.
Keywords — healthcare information system, multi-tenant SaaS, FastAPI, React, Supabase, PostgreSQL, row-level security, RBAC, electronic health records, telemedicine infrastructure, clinic management, laboratory information system
I. Introduction

Healthcare delivery in India is served by an extremely heterogeneous ecosystem — from single-doctor general practice clinics in semi-urban areas to large multi-specialty hospital chains and standalone pathology laboratories. A common challenge across these entities is the reliance on paper-based or siloed digital records, leading to inefficiency, data loss, and degraded patient care continuity [1].

The digitization of healthcare processes — often referred to as the transition to Electronic Health Records (EHR) — has been a priority in health informatics for over two decades. However, existing commercial solutions either target only large hospital networks at prohibitive licensing costs, or offer only narrow, domain-specific tools (e.g., appointment booking alone) that fail to address the holistic workflow needs of a medical facility [2].

This paper introduces HealthCore SaaS, an integrated healthcare management platform built with modern open-source technologies. The platform is designed following a multi-tenant Software-as-a-Service (SaaS) model, which allows multiple independent medical facilities to share a single deployed infrastructure instance while maintaining strict data isolation between tenants. This architecture dramatically reduces per-facility deployment and maintenance costs while enabling elastic cloud-based scaling.

II. Related Work

Significant research exists in the domain of healthcare information systems. Bossen et al. [3] highlighted usability and workflow integration as critical factors in EHR adoption. Mohammed et al. [4] demonstrated that microservice-based architectures improve the maintainability and scalability of clinical systems over traditional monolithic designs.

Supabase, used as the Backend-as-a-Service (BaaS) foundation in this work, has been evaluated by Wieruch [5] as a strong open-source alternative to Firebase, offering Postgres-native features including Row-Level Security — a feature critical for multi-tenant data isolation, as described by Makris et al. [6].

The use of FastAPI for high-performance asynchronous REST APIs in healthcare applications was explored by Rodriguez et al. [7], who noted significant latency improvements over synchronous Flask-based alternatives. Pydantic v2's validation model has been studied by Lubanovic [8] as a reliable schema enforcement mechanism in data-intensive applications.

Prior work on patient portal design by Goldzweig et al. [9] underscores that patient-facing interfaces for appointment booking and health record access improve engagement and care adherence. This informed the design of the HealthCore patient portal module.

To the best of the authors' knowledge, no prior academic work presents a fully integrated, open-source, multi-tenant SaaS platform combining clinic management, laboratory management, patient portal, and emergency dispatch in a single cohesive system.

III. System Architecture
A. Overview

HealthCore follows a decoupled, three-tier architecture pattern:

  • Presentation Layer: React 19 Single-Page Application (SPA)
  • Application Layer: FastAPI asynchronous REST API server
  • Data Layer: Supabase PostgreSQL with RLS enforcement

B. Frontend Architecture

The frontend is a Vite-bundled React 19 TypeScript SPA. Key design decisions include:

  • AuthContext: A React Context provider manages JWT session state globally, intercepting Supabase auth state changes and propagating the identity token to all API calls.
  • API Service Layer: A centralized api.ts module constructs all authenticated HTTP requests, injecting the Bearer token header automatically.
  • Tailwind CSS: Utility-first CSS framework enables rapid, consistent UI development without custom stylesheets.
  • Lucide Icons: Consistent, accessible icon library across the interface.
C. Backend Architecture

The backend is structured following the Router–Service–Model layered pattern:

  • Routers: Thin HTTP handlers that validate inputs via Pydantic schemas and delegate to service classes.
  • Services: Business logic classes (e.g., ClinicService, LabService) containing all domain operations.
  • Models: SQLAlchemy ORM models representing database entities.
  • Schemas: Pydantic v2 models for request/response validation with strict type enforcement.

The FastAPI application is launched via Uvicorn with ASGI (Asynchronous Server Gateway Interface), enabling non-blocking I/O for concurrent request handling without the Global Interpreter Lock overhead of traditional WSGI servers.

  • 002_rls_policies.sql: All Row-Level Security policies and security-definer helper functions.
  • 003_auth_triggers.sql: Automated trigger to sync auth.users entries to public.profiles on registration, and timestamp update triggers.
V. Functional Modules
A. Multi-Tenant Organization Management

Every medical facility is registered as an Organization entity, classified as one of three facility types:

  • clinic — Single-doctor general practice
  • hospital — Multi-specialty inpatient/outpatient
  • diagnostic_center — Pathology laboratory

Organization membership is tracked in a separate junction table with role and status fields, enabling one user to hold different roles across multiple facilities.

B. Patient Management

Patients are registered within an organization's scope with a unique, human-readable patient code (patient_code). Patient records include:

  • Personal demographics (DOB, gender, blood group)
  • Contact information (phone, email, address)
  • Clinical metadata (allergies, emergency contacts)
  • Linkage to a user profile (optional) for patient-portal access
C. Appointment Scheduling

The scheduling module implements a slot-based booking system. Doctor availability is modeled through DoctorSchedule records (per weekday, start/end time, slot duration). Real-time available slot computation accounts for:

  • Existing confirmed appointments
  • Schedule exceptions (holidays, leave days)
  • Configurable slot duration (default: 30 minutes)

Appointment lifecycle states: scheduled → confirmed → checked_in → completed / cancelled. Timestamps are recorded at each state transition.

D. Walk-in Queue Management

The queue module assigns sequential queue numbers to walk-in patients per day. Queue entries support both registered patients and anonymous walk-ins (via walk_in_name). Status lifecycle: waiting → called → completed / skipped.

E. Electronic Prescriptions

Prescriptions are created in draft state and linked to a patient visit and doctor. Each prescription can contain multiple line items (PrescriptionItem) specifying medication name, dosage, frequency, route, and duration. The finalization workflow transitions the prescription to a signed, immutable state. A PDF generation endpoint (GET /prescriptions/{id}/pdf) dynamically renders clinic-branded prescription documents using ReportLab.

F. Invoicing and Payments

The billing module generates itemized invoices linked to appointments or visits. Invoice computation applies: total = subtotal − discount + tax. Payment recording updates the amount_paid and balance fields in real time. Payment methods supported: cash, UPI, card, bank transfer, and others. Invoice PDF export is provided analogous to prescriptions.

G. Follow-Up Tracking

Doctors can schedule follow-up appointments with reason and target date. The module provides filterable lists by doctor, status, and date range, enabling proactive care continuity management.

H. Dashboard and Reporting

A clinic dashboard endpoint aggregates daily statistics:

  • Total appointments and queue depth
  • Revenue collected vs. outstanding balance
  • Active prescriptions and pending follow-ups

Monthly reporting aggregates appointment counts and revenue by calendar month using SQL window functions.

I. Laboratory Management

The lab module implements a complete Laboratory Information System (LIS):

  1. Test Catalogue: Each diagnostic centre maintains its own test catalogue with test codes, categories, specimen types, prep instructions, turnaround times, and pricing.
  2. Lab Orders: Doctors place multi-test orders against patients, generating a unique order number. Orders track status through: pending → sample_collected → processing → partial_results → completed.
  3. Sample Tracking: Physical specimens are assigned a unique sample reference. Lifecycle: pending_collection → collected → received → processing → rejected / completed. Rejection reasons are recorded for quality control.
  4. Result Entry and Validation: Technicians enter results with values, units, and reference ranges. Results are flagged as normal / low / high / critical. A pathologist validation step is required before results are released. An audit history (LabResultHistory) records every change.
  5. Diagnostic Reports: Consolidated reports are generated from completed orders. Report delivery events track the channel (email, SMS, in-app, printed) and delivery status.
  6. Lab Dashboard: Summary statistics for pending orders, samples awaiting collection, results pending validation, and completed tests.
J. Patient Self-Service Portal

The patient portal exposes a dedicated API prefix (/api/v1/patient) with the following capabilities:

  • Profile Management: Patients manage their own health profile, including allergies, contact details, and emergency contacts.
  • Provider Discovery: Full-text search for clinics, hospitals, and diagnostic centres by name, specialty, city, or facility type.
  • Doctor Slot Availability: Patients query real-time available appointment slots for a specific doctor on a given date.
  • Appointment Booking: Direct appointment creation with duplicate-slot prevention.
  • Appointment History: Filterable list of past and upcoming appointments.
  • Patient Dashboard: Summary of upcoming visits, total appointment count, and quick action links.
K. Emergency Ambulance Dispatch

The ambulance module provides a prototype emergency services integration:

  • Patients raise emergency requests specifying pickup location (address + GPS coordinates), emergency type (Cardiac, Accident, Respiratory, General), and contact details.
  • Ambulance vehicles are registered to hospital fleets with vehicle type, driver details, service area, and real-time GPS coordinates (base and current).
  • Operators accept, dispatch, and track requests through a status lifecycle: requested → accepted → on_the_way → arrived → completed / rejected / cancelled.
  • Simulated GPS tracking provides prototype ETA and location data for demonstration purposes.
VI. Security Architecture
A. Authentication

Authentication is handled by Supabase Auth, which issues signed JWT tokens on successful email/password login. The FastAPI backend independently verifies these tokens using PyJWT with the Supabase JWT secret, without a round-trip to Supabase on every request. The token payload contains the user's UUID, which is used as the identity anchor for all downstream authorization checks.

B. Role-Based Access Control (RBAC)

HealthCore implements a five-tier scoped RBAC model:

platform_adminGlobalFull platform access
organization_ownerPer-tenantStaff, settings, billing
doctorPer-tenantPatients, prescriptions, schedules
receptionistPer-tenantQueue, appointments, check-in
lab_staffPer-tenantTests, samples, results
Table III — RBAC Role Definitions

The get_current_user dependency in FastAPI validates the JWT, retrieves the user profile, and checks organization membership. Endpoint-level role guards are applied via allowed_roles parameter on the membership verification function.

C. Row-Level Security (RLS)

PostgreSQL RLS policies enforce data isolation at the database level, providing a defense-in-depth layer independent of application logic. Three security-definer functions provide non-recursive, performant permission checks:

  • is_platform_admin() — Global admin check
  • is_org_member(target_org_id) — Active membership check
  • is_org_owner(target_org_id) — Ownership check
Tenancy Invariant: A user holding any role in Organization A can never access data belonging to Organization B. Every query is filtered by organization_id, and cross-tenant access returns HTTP 403.
D. CORS and Transport Security

Cross-Origin Resource Sharing (CORS) is configured via FastAPI middleware, restricting allowed origins to the configured frontend domain. All production deployments are expected to enforce HTTPS at the reverse proxy or CDN layer.

B. Project Structure

The codebase follows a feature-modular layout:

  • backend/app/models/ — ORM model definitions (6 files: user, organization, clinic, lab, ambulance, provider)
  • backend/app/schemas/ — Pydantic schema definitions (7 files)
  • backend/app/routers/ — HTTP endpoint handlers (9 files)
  • backend/app/services/ — Business logic layer (8 service classes)
  • backend/app/utils/ — PDF generation utilities
  • database/migrations/ — Versioned SQL migration scripts
  • frontend/src/ — React components, pages, contexts, services
C. Testing Strategy

The test suite uses Pytest with Pytest-Asyncio for asynchronous test support. An in-memory SQLite engine (via aiosqlite) replaces the production PostgreSQL database during tests, enabling fast, isolated unit and integration tests without external dependencies. Key test coverage areas include:

  • Authentication token validation and rejection
  • Organization creation and membership enforcement
  • Clinic service operations (patient CRUD, appointment creation)
  • Lab order lifecycle state transitions
  • RBAC guard enforcement for restricted endpoints
D. PDF Generation

The pdf_generator.py utility module generates clinic-branded PDF documents for prescriptions and invoices using the ReportLab library. PDFs are streamed to the client as binary attachments via FastAPI's StreamingResponse, avoiding temporary file I/O.

B. Data Model Completeness

The system defines 22+ ORM models covering the complete patient care cycle from registration through discharge and follow-up, laboratory workflow from order to report delivery, and emergency dispatch from request through completion. This compares favorably with commercially available open-source HIS solutions such as OpenMRS (which focuses only on medical records) and GNU Health (which lacks a modern SPA frontend).

C. Security Posture

Three complementary security layers are enforced:

  1. Application-layer RBAC — Python dependency injection guards
  2. Database-layer RLS — PostgreSQL policy enforcement
  3. Transport-layer authentication — JWT signature verification

This defense-in-depth approach ensures that even a compromised application logic path cannot expose cross-tenant data, as the database layer independently enforces tenant isolation.

D. Performance Characteristics

The asynchronous architecture (FastAPI + asyncpg + async SQLAlchemy) enables handling of multiple concurrent database queries without thread-blocking. The stateless API design (all state in the database, no server-side sessions) enables horizontal scaling via standard container orchestration (e.g., Kubernetes).

IX. Future Work

Several directions for future enhancement have been identified:

  1. Telemedicine Integration: Real-time video consultation capabilities using WebRTC, enabling virtual appointment sessions directly within the patient portal.
  2. AI-Assisted Diagnostics: Integration of machine learning models for clinical decision support — e.g., drug interaction checking in prescriptions, and anomaly flagging in lab results against population reference ranges.
  3. HL7 FHIR Compliance: Implementing FHIR R4 API endpoints to enable interoperability with national health record networks (Ayushman Bharat Digital Mission) and third-party healthcare applications.
  4. Push Notifications: Real-time patient-facing notifications for appointment reminders, queue position updates, and lab result availability via FCM or APNs.
  5. Mobile Applications: React Native cross-platform mobile apps for both the staff dashboard and the patient portal, leveraging the existing REST API without backend changes.
  6. Advanced Analytics: Time-series dashboards for hospital administrators — disease burden analytics, revenue forecasting, and staff utilization reports.
  7. Real GPS Tracking: Integration with a live GPS tracking provider for the ambulance dispatch module, replacing the current prototype simulation.
  8. HIPAA/DPDPA Compliance Audit: Formal security audit and compliance mapping to India's Digital Personal Data Protection Act (DPDPA) 2023 and international HIPAA standards.
X. Conclusion

This paper presented HealthCore SaaS, a comprehensive, multi-tenant healthcare management platform built on modern open-source cloud-native technologies. The system addresses the critical gap in affordable, integrated digital healthcare infrastructure for small and medium medical facilities in India.

The platform's key innovations include its strict tenant isolation model enforced at both application and database levels, the integration of five major functional modules (clinic management, laboratory management, patient portal, emergency dispatch, and provider directory) in a single cohesive system, and its use of asynchronous Python and React 19 for high-performance, scalable delivery.

The implementation demonstrates that modern open-source technologies — FastAPI, Supabase, React, SQLAlchemy — can be combined to produce production-grade healthcare software without proprietary licensing costs, making digital transformation accessible to a broader segment of India's healthcare ecosystem.

The codebase and architecture serve as a strong foundation for future extensions toward telemedicine, AI-assisted diagnostics, and national health network interoperability.
